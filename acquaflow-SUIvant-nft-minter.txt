## 1. Executive Summary

The current NFT ecosystem is plagued by three critical failures: **static assets** that cannot evolve with gameplay, **storage fragility** where "immutable" assets break when metadata providers vanish, and **liquidity fragmentation** across isolated blockchains.

**Sui Generis** is a next-generation minting and management protocol designed to solve these issues. By leveraging the **Sui Network’s object-centric architecture** as the primary engine for dynamic GameFi assets, and bridging to EVM chains via a unique **ENS Fail-Safe Resolution Strategy**, Sui Generis creates "Sovereign Objects." These assets are dynamic, composable, and permanently retrievable, regardless of the underlying storage provider.

This platform empowers creators, game studios, and collectors to mint assets that are "born on Sui" but "live everywhere," managed by autonomous AI agents via the **Agent-to-Agent (A2A) Protocol**.

## 2. Strategic Architecture

The platform utilizes a **Hybrid "Dual-Core" Architecture** that abstracts the complexity of multi-chain minting while preserving the unique advantages of each network.

### 2.1 The Core Engines

* **The Sui Core (Primary):** Utilizes Move objects for high-frequency, dynamic assets (e.g., game items that level up). Assets here are not just database entries; they are distinct digital objects stored in the user's "Kiosk."
* **The EVM Core (Secondary):** Utilizes Solidity contracts (ERC-721/1155 + ERC-6551) for broad market reach on Ethereum, Base, and Polygon. These assets mirror the Sui utility where possible using Token Bound Accounts.

### 2.2 The ENS "Fail-Safe" Storage Layer (The .ens Strategy)

We eliminate the industry-standard risk of "dead links" (404 errors) for NFT metadata.

* **Traditional Model:** Hardcoded `ipfs://Qm...` hash. If Pinata/IPFS fails or the account closes, the NFT is broken forever.
* **Sui Generis Model:** The Smart Contract points to a mutable **ENS Text Record** (e.g., `metadata.acqua-game.eth`).
* **Resolution:** The contract queries the ENS record  Gets the current IPFS CID  Resolves data.
* **Recovery:** If a storage provider fails, the Admin updates the ENS record to a new provider (e.g., Arweave). The Smart Contract remains untouched, and the NFT repairs itself instantly.



### 2.3 The Agent-to-Agent (A2A) Automation Layer

Operations are managed by autonomous AI agents, not manual admin panels.

* **Minting Agent:** Monitors gas prices and executes batch mints when costs are optimal.
* **Liquidity Agent:** Automatically interacts with marketplace agents (e.g., Uniswap v4 Hooks) to provision liquidity pools for newly minted collections.

## 3. Unique SUI Features Highlights

We chose Sui not just for speed, but for its fundamental data architecture which aligns with complex GameFi needs.

### 3.1 Object-Centricity vs. Account-Centricity

On EVM, an NFT is a balance in a contract. On Sui, an NFT is an **Object** owned directly by an address. This allows for parallel processing (massively scalable mints) and true ownership.

### 3.2 The "Sui Kiosk" Standard

We implement `0x2::kiosk` for all assets.

* **Enforced Royalties:** Royalty policies are bound to the Kiosk, guaranteeing creators get paid on *every* trade, unlike the optional royalty systems on EVM marketplaces.
* **Safe Listing:** Assets can be listed for sale without leaving the user's wallet until the trade executes.

### 3.3 Dynamic Fields & Composability

Our NFTs utilize **Dynamic Fields** to store mutable game data on-chain.

* *Example:* A "PaddleBoard" NFT can have a dynamic field `navigated_distance` , or `collected_plastics_weight`. As the player uses it in-game, the NFT itself updates the amount of collected items and navigated distance.
* *Nesting:* We support **Composable NFTs**, where any NFT, like an Avatar NFT "owns" its Inventory NFTs. Selling the Avatar transfers the entire inventory in a single atomic transaction.

The Concept: Dynamic Resolution using a mutable IPFS hash the contract will fetch
Instead of hardcoding a static ipfs:// string (which breaks if the IPFS pin is lost), this contract asks the ENS Registry for the current location of your data every time a user or marketplace requests the NFT image.

This code embodies the "sovereign" nature of the ACQUAFLOW protocol. The contract doesn't contain the data location; it knows how to ask for it. This grants the creator absolute sovereignty over where asset data lives (IPFS, Arweave, Swarm) without ever needing to upgrade the smart contract itself.

** ENS Text Record Resolver** (Solidity) to demonstrate how the contract fetches the mutable IPFS hash
This Solidity contract implements the ENS Text Record Resolver strategy. This approach creates a "Fail-Safe" link between your contract and your metadata.


// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

import "@openzeppelin/contracts/token/ERC721/ERC721.sol";
import "@openzeppelin/contracts/access/Ownable.sol";
import "@openzeppelin/contracts/utils/Strings.sol";

// Interface to interact with the ENS Registry (to find the Resolver)
interface IENS {
    function resolver(bytes32 node) external view returns (address);
}

// Interface to interact with the Resolver (to get the Text Record)
interface IResolver {
    function text(bytes32 node, string calldata key) external view returns (string memory);
}

/**
 * @title SuiGeneris (Fail-Safe NFT)
 * @dev An NFT contract that resolves its metadata BaseURI from an ENS Text Record.
 * This allows the project owner to switch storage providers (IPFS -> Arweave)
 * without deploying a new contract or paying gas to update 10,000 token URIs.
 * Implements the ENS Prize strategy[cite: 360, 363].
 */
contract SuiGeneris is ERC721, Ownable {
    using Strings for uint256;

    // The ENS Registry Address (Mainnet: 0x00000000000C2E074eC69A0dFb2997BA6C7d2e1e)
    IENS public immutable ensRegistry;
    
    // The ENS Namehash for your project (e.g., "acqua-assets.eth")
    // Use a tool like eth-ens-namehash to generate this offline.
    bytes32 public projectNode;

    // The specific key in the ENS Text Record to look for (e.g., "url")
    // This leverages the ENS Text Record feature.
    string public metadataKey = "url";

    // Fallback URI in case ENS is completely unreachable (Safety Net)
    string public fallbackURI;
    bool public useFallback = false;

    constructor(
        address _ensRegistry,
        bytes32 _projectNode, 
        string memory _fallbackURI
    ) ERC721("Sui Generis Assets", "SGA") Ownable(msg.sender) {
        ensRegistry = IENS(_ensRegistry);
        projectNode = _projectNode;
        fallbackURI = _fallbackURI;
    }

    /**
     * @notice The Magic Function: Resolves the BaseURI dynamically from ENS.
     */
    function _baseURI() internal view override returns (string memory) {
        if (useFallback) {
            return fallbackURI;
        }

        // 1. Get the Resolver address for our ENS name
        address resolverAddress = ensRegistry.resolver(projectNode);
        
        // If no resolver is set, revert to fallback to prevent breakage
        if (resolverAddress == address(0)) {
            return fallbackURI;
        }

        // 2. Query the Resolver for the specific Text Record
        try IResolver(resolverAddress).text(projectNode, metadataKey) returns (string memory ensUri) {
            // Ensure the record isn't empty
            if (bytes(ensUri).length > 0) {
                return ensUri;
            } else {
                return fallbackURI;
            }
        } catch {
            return fallbackURI;
        }
    }

    /**
     * @notice Standard tokenURI function that appends the TokenID to the dynamic base.
     * Example Result: "ipfs://QmNewHash.../1"
     */
    function tokenURI(uint256 tokenId) public view override returns (string memory) {
        _requireOwned(tokenId);

        string memory base = _baseURI();
        return string(abi.encodePacked(base, tokenId.toString()));
    }

    // --- Admin Functions for Emergencies ---

    function setProjectNode(bytes32 _newNode) external onlyOwner {
        projectNode = _newNode;
    }

    function setFallbackURI(string memory _newFallback) external onlyOwner {
        fallbackURI = _newFallback;
    }

    function toggleFallback(bool _status) external onlyOwner {
        useFallback = _status;
    }

    function mint(address to, uint256 tokenId) external onlyOwner {
        _safeMint(to, tokenId);
    }
}

The Concept: Object-Centricity
In EVM, the "PaddleBoard" is just ID #50 inside a massive contract array. In Sui, the "PaddleBoard" is its own distinct object with its own ID. 
We will mint this object directly into a Sui Kiosk to enforce royalties and safe trading rules from the moment of birth.

RUST
module acqua::game_item {
    use sui::url::{Self, Url};
    use sui::string::{Self, String};
    use sui::object::{Self, ID, UID};
    use sui::event;
    use sui::transfer;
    use sui::tx_context::{Self, TxContext};
    use sui::dynamic_field;
    
    // Standard Kiosk imports to enforce royalties/locking
    use sui::kiosk::{Self, Kiosk, KioskOwnerCap};
    use sui::transfer_policy::{Self, TransferPolicy};

    // Error Codes
    const ENotAuthorized: u64 = 0;

    // --- Structs ---

    /**
     * @dev The "GameMaster" Capability. 
     * Only the holder of this object (the Server/AI Agent) can 
     * level up items or update the storage URL.
     */
    public struct GameMasterCap has key, store {
        id: UID
    }

    /**
     * @dev The core Game Item (Hero/Weapon).
     * Unlike EVM, this object holds its own state.
     */
    public struct GameItem has key, store {
        id: UID,
        name: String,
        description: String,
        // The "Sovereign" URL. Can be updated by Admin to fix broken links.
        url: Url, 
        // Core stat (e.g., Level) stored directly on the object
        generation: u64, 
    }

    // --- Dynamic Field Keys ---
    // We use these keys to attach extra data (XP, Durability) 
    // without changing the struct layout.
    
    public struct LevelKey has copy, drop, store {}
    public struct DurabilityKey has copy, drop, store {}

    // --- Events ---
    public struct ItemLeveledUp has copy, drop {
        item_id: ID,
        new_level: u64
    }

    // --- Init ---

    fun init(ctx: &mut TxContext) {
        // Create the unique GameMaster capability and send to deployer
        transfer::transfer(GameMasterCap {
            id: object::new(ctx)
        }, tx_context::sender(ctx));
    }

    // --- Minting Logic ---

    /**
     * @notice Mints an item directly into the user's Kiosk.
     * This ensures the item is instantly tradeable but protected by policies.
     */
    public fun mint_to_kiosk(
        cap: &GameMasterCap,
        kiosk: &mut Kiosk,
        kiosk_cap: &KioskOwnerCap,
        policy: &TransferPolicy<GameItem>,
        name: vector<u8>,
        description: vector<u8>,
        url_bytes: vector<u8>,
        ctx: &mut TxContext
    ) {
        let id = object::new(ctx);
        let item = GameItem {
            id,
            name: string::utf8(name),
            description: string::utf8(description),
            url: url::new_unsafe_from_bytes(url_bytes),
            generation: 1,
        };

        // Initialize Dynamic Fields (e.g., Level 1, Durability 100)
        // We attach these *to* the item object.
        dynamic_field::add(&mut item.id, LevelKey {}, 1u64);
        dynamic_field::add(&mut item.id, DurabilityKey {}, 100u64);

        // Lock the item in the Kiosk so it can't be transferred 
        // bypassing the royalty policy.
        kiosk::lock(kiosk, kiosk_cap, policy, item);
    }

    // --- The "Dynamic" Logic (GameFi) ---

    /**
     * @notice Allows the AI Agent (via GameMasterCap) to update stats 
     * in real-time based on game events.
     */
    public fun level_up(
        _cap: &GameMasterCap, 
        item: &mut GameItem
    ) {
        // Access the dynamic field via key
        let level = dynamic_field::borrow_mut<LevelKey, u64>(&mut item.id, LevelKey {});
        *level = *level + 1;

        event::emit(ItemLeveledUp {
            item_id: object::uid_to_inner(&item.id),
            new_level: *level
        });
    }

    // --- The "Sovereign" Logic (Fail-Safe) ---

    /**
     * @notice If IPFS/Pinata fails, the Admin updates the URL here.
     * Unlike EVM, we update the object directly, not a registry.
     */
    public fun update_url(
        _cap: &GameMasterCap,
        item: &mut GameItem,
        new_url: vector<u8>
    ) {
        item.url = url::new_unsafe_from_bytes(new_url);
    }
}

The Concept: Object-Centricity
In EVM, the "Sword" is just ID #50 inside a massive contract array. In Sui, the "Sword" is its own distinct object with its own ID. We will mint this object directly into a Sui Kiosk to enforce royalties and safe trading rules from the moment of birth.

Key Technical Differences in the architecture to consider in the design: 

Direct Mutation (Sui) vs. Indirect Resolution (EVM):

EVM (Solidity): The user's wallet holds a token ID. The contract calculates the URL by asking ENS. It is a "pointer" system.

Sui (Move): The user's Kiosk holds the actual GameItem object. The update_url function physically changes the data inside that specific object.


Dynamic Fields:

In the mint_to_kiosk function, we attach LevelKey and DurabilityKey.

In EVM, adding a new stat usually requires deploying a new contract or using complex unstructured storage. In Sui, your "Sword" object effectively has its own little database attached to it that can grow as the game evolves.


Kiosk Locking:

The kiosk::lock call is critical. It forces the asset to live inside the Kiosk system. This guarantees that if the user sells the item, they must pay the royalties defined in the TransferPolicy. You cannot bypass royalties by just doing a direct wallet-to-wallet transfer like you can on Ethereum.

      target: `${SUI_PACKAGE_ID}::game_item::mint_to_kiosk`,
      arguments: [
        txb.object(GAME_MASTER_CAP_ID), // The auth cap (or use a shared object flow)
        txb.object("0xYourKioskId"),    // User's Kiosk (simplified)
        txb.object("0xYourKioskCap"),   // User's Kiosk Cap
        txb.object("0xYourTransferPolicy"),
        txb.pure("Acqua Sword"),        // Name
        txb.pure("A legendary blade"),  // Desc
        txb.pure(urlBytes)              // URL as bytes
      ],
    });

    return new Promise((resolve, reject) => {
      signAndExecuteTransactionBlock(
        { transactionBlock: txb },
        {
          onSuccess: (result) => resolve(result),
          onError: (err) => reject(err),
        }
      );
    });
  };

  /**
